# Backup Passphrase Rotation Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make backup passphrase rotation re-encrypt the database entry inside each `.tar.gz` backup with the passphrase the user saved, and let users repair or remove backups an earlier rotation damaged.

**Architecture:** A new `BackupArchiveRotator` owns the archive-level operations (inspect a file, re-encrypt its database entry, unwrap a damaged file), sharing tar entry names with `BackupService` through `BackupConstants`. A new `BackupRotationService` gives the rotation dialog a pre-check (scan), a repair step and a delete step. `RotateBackupPassphraseJob` calls the rotator per file. The dialog passes its passphrase through, and the job payload carries it protected.

**Tech Stack:** .NET 10, Blazor Server, MudBlazor 9, Quartz.NET (persistent Postgres store), System.Formats.Tar, GZipStream, AES-256-GCM (`IBackupEncryptionService`), NUnit 4, NSubstitute 6, bUnit.

**Spec:** No separate spec file. The design was agreed in the session on 2026-10-02 and is summarized under "Design" below.

## Design

**Root cause (bug 1).** Since backup format 3.0 a backup is a `.tar.gz` with `metadata.json`, `database.json.enc` (AES-GCM, `TGAEC2`) and `media/ban-gifs/*`. `RotateBackupPassphraseJob` still treats a file as one encrypted blob. It checks the whole file for a `TGAENC`/`TGAEC2` header, finds gzip, and decides the file is unencrypted. It then encrypts the whole archive with the new passphrase (legacy single-shot `TGAENC`) and stores the new passphrase. The database entry inside stays on the old passphrase, which is no longer stored anywhere. Its validation only checks the outer layer, so it reports success.

**Bug 2.** `BackupPassphraseRotationDialog` shows the user a passphrase (generated, or custom) and tells them to save it. `OnComplete` then calls `RotatePassphraseAsync(backupDirectory, userId)`, which generates a different passphrase. The user's saved copy is never used, and a custom passphrase is ignored.

**Damaged files in the wild (open-source, other installs may have rotated).** A rotated file has exactly one outer `TGAENC` layer, keyed with the stored passphrase. A second rotation unwraps it with the old passphrase and re-wraps it with the new one. Inside is a normal archive whose database entry uses the passphrase that was current when the backup was made. That inner passphrase is recoverable only if the user knows it. That is usually the setup passphrase. A passphrase generated by an earlier rotation (bug 2) was never shown, so those files can't be recovered.

**Agreed behaviour.**
1. Rotation re-encrypts only the `database.json.enc` entry. Metadata and media are copied byte-for-byte. A plain `database.json` (legacy, unencrypted) is encrypted and renamed to `database.json.enc`.
2. Every rewrite goes to a temp file next to the backup. It is verified by reading the metadata and fully decrypting the new entry with the target passphrase, then swapped in with `File.Move(..., overwrite: true)`.
3. Re-running is safe. A file whose entry already opens with the new passphrase is left alone and counted as already current.
4. **Pre-check.** Opening the rotation dialog scans the backup directory first. Wrapped files go to a repair step, which asks for the passphrase used before the first rotation. The stored passphrase opens the outer layer, so the user supplies only the inner one. The user can try several passphrases. Each try repairs every file that one opens, re-encrypting its entry with the stored passphrase so the file becomes a normal backup.
5. Wrapped files that stay locked, and unreadable files, are listed with an explicit **Delete these N backups** action (confirmed) next to **Continue without them**. Deleting writes an audit entry.
6. The job skips wrapped files with a warning. They never block the passphrase update. Unreadable files still count as failures and keep the old passphrase stored.
7. The dialog's passphrase is the one used. `RotatePassphraseAsync(newPassphrase, backupDirectory, userId)` protects it with `IDataProtectionService` before it goes into the Quartz payload, and the job unprotects it.

## Review Focus

- A backup directory holding a mix of healthy, plain, wrapped and unreadable files: rotation must rotate the healthy and plain ones, skip the wrapped ones, fail on unreadable ones, and keep the old passphrase stored on any failure.
- A job that failed half-way and is run again: files already on the new passphrase must be counted as current, not fail with a decryption error.
- A repair passphrase that opens only some wrapped files: those are repaired, the rest stay wrapped and untouched, and the dialog lists exactly the rest.
- A file name sent to delete that resolves outside the backup directory, or a file that is no longer wrapped or unreadable: never deleted.
- A queued job created by an older build, whose payload has `NewPassphrase` and no protected field: the job logs an error and exits without changing files or config.

- [ ] **Step 4: Implement `BackupArchiveRotator`**

Constructor: `(IBackupEncryptionService encryption, RecyclableMemoryStreamManager streams, ILogger<BackupArchiveRotator> logger)`.

- **`InspectAsync`:** read the first 7 bytes. If they equal `EncryptionConstants.LegacyMagicHeader` or `ChunkedMagicHeader`, return `Wrapped`. If they start with `1f 8b`, walk the tar entries and return `Encrypted` or `Plain` for the first database entry found, or `Unreadable` if there is none. Map any `InvalidDataException`, `EndOfStreamException` or `FormatException` while walking to `Unreadable`. Anything else is `Unreadable`.
- **`ReencryptAsync`:**
  1. Inspect, and throw `InvalidOperationException` unless the state is `Encrypted` or `Plain`.
  2. Read the database entry into a pooled stream. If it's encrypted, decrypt with `oldPassphrase`. On `CryptographicException`, try `newPassphrase`: if that succeeds, return `AlreadyCurrent` without writing anything; if it fails, rethrow the original exception.
  3. Encrypt the plaintext with `newPassphrase`. Write `{path}.{guid8}.tmp` by streaming the source entries in order. Metadata and media are copied with `WriteEntryAsync(new PaxTarEntry(TarEntryType.RegularFile, entry.Name) { DataStream = copy })`. The database entry is written under `EncryptedDatabaseEntryName` with the new ciphertext.
  4. Verify the temp file: inspect it as `Encrypted`, read its metadata entry, and fully decrypt its database entry with `newPassphrase`. The decrypted length must equal the plaintext length.
  5. `File.Move(temp, path, overwrite: true)`, then return `Reencrypted`.
  6. Delete the temp file in a `finally` if it still exists.
- **`TryRepairWrappedAsync`:**
  1. Decrypt the whole file with `storedPassphrase` into `{path}.{guid8}.inner.tmp`. A `CryptographicException` propagates.
  2. Inspect the inner file. It must be `Encrypted`; otherwise delete the temp file and throw `InvalidOperationException`.
  3. Try to decrypt its database entry with `originalPassphrase`. On `CryptographicException`, delete the temp file and return false.
  4. Re-encrypt the inner file from `originalPassphrase` to `storedPassphrase`, using the same private helper that `ReencryptAsync` uses, with the temp file as the source.
  5. Verify as in `ReencryptAsync`, move into place, and return true.

Factor the "rewrite archive with a new database ciphertext and verify" logic into one private method used by both public methods.
